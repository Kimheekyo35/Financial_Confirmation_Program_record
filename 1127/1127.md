## 21번
```
한 전자 상거래 회사가 AWS에서 하루에 한 번 거래하는 웹 사이트를 시작하려고 합니다. 매일 24시간 동안 정확히 하나의 제품이 판매됩니다. 회사는 피크 시간 동안 밀리초의 대기 시간으로 매시간 수백만 건의 요청을 처리할 수 있기를 원합니다. 최소한의 운영 오버헤드로 이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

① A. Amazon S3를 사용하여 다양한 S3 버킷에서 전체 웹 사이트를 호스팅하십시오. Amazon CloudFront 배포를 추가합니다. S3 버킷을 배포 원본으로 설정합니다. Amazon S3에 주문 데이터를 저장합니다.
② B. 여러 가용 영역에 걸쳐 Auto Scaling 그룹에서 실행되는 Amazon EC2 인스턴스에 전체 웹 사이트를 배포합니다. 웹 사이트 트래픽을 분산하려면 ALB(Application Load Balancer)를 추가하세요. 백엔드 API를 위한 또 다른 ALB를 추가합니다. MySQL용 Amazon RDS에 데이터를 저장합니다.
③ C. 컨테이너에서 실행되도록 전체 애플리케이션을 마이그레이션합니다. Amazon Elastic Kubernetes Service(Amazon EKS)에서 컨테이너를 호스팅합니다. Kubernetes Cluster Autoscaler를 사용하여 트래픽 버스트를 처리할 Pod 수를 늘리거나 줄입니다. MySQL용 Amazon RDS에 데이터를 저장합니다.
④ D. Amazon S3 버킷을 사용하여 웹 사이트의 정적 콘텐츠를 호스팅합니다. Amazon CloudFront 배포를 배포합니다. S3 버킷을 원본으로 설정합니다. 백엔드 API에는 Amazon API Gateway 및 AWS Lambda 함수를 사용하십시오. Amazon DynamoDB에 데이터를 저장합니다.
```

- 1번: S3는 HTML, CSS, JavaScript, 이미지 같은 **정적 콘텐츠**를 호스팅할 수 있음. 그리고 CloudFront는 S3의 콘텐츠를 엣지 로케이션 (edge location)에 캐싱해 사용자에게 빠른 전달 가능.

    ▶ S3는 객체 스토리지이므로, 빠른 데이터 읽기와 쓰기가 필요한 트랜잭션용 데이터베이스가 아님.
    
    ▶ 사용자의 주문 요청을 받아 처리할 **백엔드 처리 계층이 없음.**

- 2번: **최소한의 운영 오버헤드**를 충족시키지 못함. 또한, RDS는 **활성화한다**는 문구가 있어야 함. EC2 운영체제 패치, 서버 설정, 배포와 확장 정책 관리가 필요함.
- 3번: EKS + 컨테이너 + RDS -> **운영 복잡성 큼**

    ▶ 위와 같은 이유로, EK에서 애플리케이션 실행 개수를 늘려 대량 요청을 처리할 수 있음. 하지만 **컨테이너 배치, 자원 설정, 확장 구성 등 관리할 것이 많음.**
- 4번: s3 + cloudfront → 정적 콘텐츠, **정적 콘텐츠**를 주문할 수 없는 화면이라고 이해. 화면 파일 S3, 주문 버튼을 누르면 API Gateway + Lambda 통해 주문 가능하므로 직접 관리해야하는 부분이 적음.

    ▶ 화면, 이미지 제공 : S3 + CloudFront
    
    ▶ 주문 요청 접수: API Gateway

    ▶ 주문 처리: Lambda

    ▶ 상품 및 주문 저장: DynamoDB (nosql로 대용량 데이터 저장에 용이)


## 22번
```
솔루션 설계자는 Amazon S3를 사용하여 새로운 디지털 미디어 애플리케이션의 스토리지 아키텍처를 설계하고 있습니다. 미디어 파일은 가용 영역이 손실되더라도 복원력이 있어야 합니다. 일부 파일은 자주 액세스되는 반면 다른 파일은 예측할 수 없는 패턴으로 거의 액세스되지 않습니다. 솔루션 설계자는 미디어 파일 저장 및 검색 비용을 최소화해야 합니다.
이러한 요구 사항을 충족하는 스토리지 옵션은 무엇입니까?
① A. S3 표준
② B. S3 지능형 계층화(S3 Intelligent-Tiering)
③ C. S3 스탠다드-Infrequent Access(S3 스탠다드-IA)
④ D. S3 One Zone-Infrequent Access(S3 One Zone-IA)
```

1. S3 표준: 여러 가용 영역에 저장하므로 복원력 조건은 해당. 하지만 거의 읽지 않은 데이터에도 standard 요금이 적용되어 비용 측면에서 옳지 않음
2. S3 Intelligent-Tiering (지능형 계층화): 여러 가용 영역에 저장하고, 파일별 조회 빈도에 따라 저장 계층을 자동 조정함. 소액의 모니터링 및 자동화 요금은 있지만 **별도의 데이터 검색 요금은 없어 조회 패턴이 불규칙한 상황**에 적합함.
3. S3 스탠타드 - IA: 여러 가용 영역에 저장하고 저장 단가도 낮지만, 읽어온 데이터 용량에 따라 검색 요금이 붙음. 따라서 자주 조회되는 파일까지 이 클래스에 두면 비용면에서 불리.
4. S3 OneZone - IA: 한 가용 영역에만 저장하므로, 해당 가용 영역이 손실되면 파일 보존을 보장할 수 없음.

## 23번

① A. 객체를 자동으로 마이그레이션하도록 S3 Intelligent-Tiering을 구성합니다.
② B. 1개월 후에 S3 Standard에서 S3 Glacier Deep Archive로 객체를 전환하기 위한 S3 수명 주기 구성을 생성합니다.
③ C. 1개월 후에 객체를 S3 Standard에서 S3 Standard-Infrequent Access(S3 Standard-IA)로 전환하기 위한 S3 수명 주기 구성을 생성합니다.
④ D. 1개월 후에 객체를 S3 Standard에서 S3 One Zone-Infrequent Access(S3 One Zone-IA)로 전환하기 위한 S3 수명 주기 구성을 생성합니다.

3. **S3 Standard - IA**는 조회할 때 검색 요금이 계속 붙고, Glacier Deep Archive 보다 높은 저장 단가로 계속 보관한다는 점이 핵심
4. 비용 측면에서 옳지 않음, 한 가용 영역에만 저장하므로 해당 영역이 영구적으로 손실되면 백업도 잃을 수 있음.

## 24번
```

## 25번
```
회사에서 애플리케이션을 설계하고 있습니다. 애플리케이션은 AWS Lambda 함수를 사용하여 Amazon API Gateway를 통해 정보를 수신하고 해당 정보를 Amazon Aurora PostgreSQL 데이터베이스에 저장합니다.
개념 증명 단계에서 회사는 데이터베이스에 로드해야 하는 대량의 데이터를 처리하기 위해 Lambda 할당량을 크게 늘려야 합니다. 솔루션 설계자는 확장성을 향상하고 구성 노력을 최소화하기 위해 새로운 디자인을 권장해야 합니다.
이러한 요구 사항을 충족하는 솔루션은 무엇입니까?

① A. Amazon EC2 인스턴스에서 실행되는 Apache Tomcat 코드로 Lambda 함수 코드를 리팩터링합니다. 기본 JDBC(Java Database Connectivity) 드라이버를 사용하여 데이터베이스를 연결합니다.
② B. 플랫폼을 Aurora에서 Amazon DynamoDProvision DynamoDB Accelerator(DAX) 클러스터로 변경합니다. DAX 클라이언트 SDK를 사용하여 DAX 클러스터에서 기존 DynamoDB API 호출을 가리킵니다.
③ C. 두 개의 Lambda 함수를 설정합니다. 정보를 수신하는 하나의 기능을 구성하십시오. 정보를 데이터베이스에 로드하도록 다른 기능을 구성하십시오. Amazon Simple 알림 서비스(Amazon SNS)를 사용하여 Lambda 함수를 통합합니다.
④ D. 두 개의 Lambda 함수를 설정합니다. 정보를 수신하는 하나의 기능을 구성하십시오. 정보를 데이터베이스에 로드하도록 다른 기능을 구성하십시오. Amazon Simple Queue Service(Amazon SQS) 대기열을 사용하여 Lambda 함수를 통합합니다.
```

### AMAZON SNS & SQS
- SNS : 양쪽 모두, 정확히 동시에 도착한다는 거보단 구독자마자 같은 이벡트를 받아 각자 할 일을 함.
- SQS : 주문 1000건을 여러 작업자가 **나눠서** DB에 저장

### Apache Tomcat, DynamoDB Accelerator
- Apache Tomcat: Java 웹 애플리케이션을 실행시키는 서버. "Tomcat 코드로 리팩토링"은 Lambda에서 실행하던 코드를 EC2의 Tomcat에서 실행하도록 고친다는 뜻.
- DAX (DynamoDB Accelerator): DynamoDB에서 **같은 데이터를 반복해서 읽을 때 응답을 빠르게** 해 주는 캐시. DAX의 주된 강점은 **읽기**임. 하지만 문제의 요구사항은 **쓰기**임.

3. Lambda 두 개 + SNS: SNS로 저장용 Labmda를 호출할 수 있음. 하지만 여러 구독자에게 알릴 필요가 없고, 요청이 몰렸을 때 **아직 저장하지 못한 작업을 쌓아 두고 처리량을 조절**하는 게 중요
4. Lambda 두 개 + SQS: 수신용 Lambda는 메시지를 queue에 넣고 종료함. 저장용 Lambda는 큐에서 메시지를 묶음으로 받아 Aurora에 기록함. 동시에 실행되는 저장용 Lambda수를 Aurora가 감당할 수준으로 제한하면 나머지는 queue에서 기다림

## 26번
```
회사는 Amazon S3 버킷에 무단 구성 변경이 없는지 확인하기 위해 AWS 클라우드 배포를 검토해야 합니다. 이 목표를 달성하려면 솔루션 아키텍트가 무엇을 해야 합니까?

① A. 적절한 규칙을 사용하여 AWS Config를 활성화합니다.
② B. 적절한 점검을 통해 AWS Trusted Advisor를 활성화합니다.
③ C. 적절한 평가 템플릿을 사용하여 Amazon Inspector를 활성화합니다.
④ D. Amazon S3 서버 액세스 로깅을 활성화합니다. Amazon EventBridge(Amazon Cloud Watch 이벤트)를 구성합니다.
```

- AWS Config: S3 버킷의 **구성 변경 이력**을 기록하고, 변경된 설정이 **지정한 규칙을 준수**하는지 평가.
- AWS Trusted Advisor: 보안, 비용, 성능에서 AWS 모범 사례를 기준으로 개선점을 권고. 이 문제에서 필요한 버킷별 구성 변경 추적과 규칙 평가는 *Config*가 함.
- Amazon Inspector: EC2, 컨테이너 이미지, Lambda 함수 등에서 **소프트웨어 취약점** 찾음. EC2의 취약점을 찾아줘 → Amazon Inspector가 맞음.
- S3 서버 엑세스 로깅 + Amazon EventBridge: S3 서버 엑세스 로깅은 S3에 들어온 요청을 기록하고, Eventbridge는 **이벤트**를 전달. 버킷 설정이 회사 규칙을 준수하는 지는 확인하지 않음.

## 27번
```
한 회사가 새로운 애플리케이션을 출시하고 있으며 Amazon CloudWatch 대시보드에 애플리케이션 지표를 표시합니다. 회사의 제품 관리자는 이 대시보드에 정기적으로 액세스해야 합니다. 제품 관리자에게는 AWS 계정이 없습니다. 솔루션 설계자는 최소 권한 원칙에 따라 제품 관리자에 대한 액세스를 제공해야 합니다.
이러한 요구 사항을 충족하는 솔루션은 무엇입니까?
